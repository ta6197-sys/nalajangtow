# Phase 2 — 168-hour look-ahead integration report

Base `0253682517a4d8a70e0927250d978e7b55d254e0`, branch `feat/v2-phase2-rolling-forecast`. The final Phase 1 weather-event commit is not part of this base because it had not been merged into main when this branch was created.

`LOOKAHEAD_168H_V1` defines 168-hour forecast, 72-hour optimization, 24-hour freeze, 24-hour step and 30-minute inventory interval. The legacy policy remains available. The existing scheduler and its objective are untouched; the new service and `GET /api/forecast/v1?run_id=<uuid>` are opt-in read-only calls over a frozen snapshot, with no DB writes, schedule confirmation or solver invocation. The forecast carries full supplied occupancy intervals, including work continuing past the detailed horizon. No physical timestamps are rounded.

Only calls with `known_at <= as_of` and availability before the forecast end are displayed. Confirmed occupancy requires a confirmation timestamp no later than the snapshot time; previous tentative occupancy requires its own `known_at`. Missing provenance is reported instead of inferring it. Supplied uncertain forecasts need an identifier, provenance, known time and prediction time, and never become hard constraints or assignments. Same-berth interval conflicts and full active-berth occupancy are reported as confirmed or potential depending on evidence. Unassigned demand and missing data are explicit. There is no inferred tank, FIX, pilotage or future weather policy.

Acceptance status: time boundaries, deterministic output, no forecast writes, and unchanged legacy solver implementation are verified. Tests cover known-at leakage for calls, commitments, tentative assignments and uncertain predictions. Complete historical provenance for contract and berth master revisions is not available in the snapshot schema, so future-information exclusion for those fields is not independently established. The existing database snapshot does not preserve selection-known time for prior tentative plans, and the service therefore cannot safely carry those plans as forecast occupancy until that provenance is provided. FIX demand and useful solver hints are pending verified inputs and integration. No forecast result is operationally executable. Phase 2 is not yet fully accepted; resolve these gaps before Phase 3.

## Follow-up: available-data closeout

The feature branch was recreated from main `d4af552` after Phase 1 and the initial Phase 2 commits were merged. The API now recovers prior selected-plan provenance only when the recorded assignment, call, berth, times, candidate, experiment, previous run and selection confirmation match and confirmation was known by the new planning timestamp. It returns a separate provenance hash. An actual historical selection in the isolated source copy had a confirmation timestamp after the later planning timestamp, and was correctly excluded. An explicitly synthetic earlier timestamp was included in a rollback-only test, and the original database record was restored. Confirmation metadata and forecast physical timestamps retain seconds; this does not alter unresolved contractual settlement precision.

Contract and berth master history remain unverified and are shown in `missing_data`. With no as-of berth-master provenance, the service does not use the current active-berth list to calculate historical congestion or validate historical berth membership. A source-backed master with an explicit known time is required for that calculation. The user accepted this limitation as pending data; it does not establish the original master's historical correctness.

`forecast.hints.validated_planning_hint()` optionally checks the original snapshot hash, exact policy boundaries, original tentative rows, and supplied weather fingerprint, then independently replays a 72-hour tentative plan before returning a read-only hint. The optimizer does not consume it automatically; it is not confirmation or a hard forecast constraint. Missing selected-plan or physical inputs remain explicit.

Final checks: 193 tests run, 192 passed, one existing fresh-initial-state PostgreSQL test skipped; isolated PostgreSQL provenance test passed including rollback; the forecast API OpenAPI syntax check passed. The prior Phase 1 results are preserved on main, with the event version disabled by default. No operational PostgreSQL state was changed.

Status: available-data implementation and verification are complete, with explicit limits. Strict historical master-provenance and FIX-demand acceptance cannot be established without source information, and the original fresh-state PostgreSQL integration remains skipped. Any move to Phase 3 must preserve those open items and must not describe the forecast as operationally ready.
