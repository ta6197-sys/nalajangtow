- 기준: GitHub `ta6197-sys/nalajangtow` / `main` 커밋 `db8b78dde0488c5598bd55c4c527820b03af8868` (PR #70 병합 시점).
- 기준 운영 규칙: `V5_USER_ETU_SWITCHING_20261112_V1` (PR #69).
- 사용자 확인: 로컬/Docker Python 3.11 환경 재검증은 **완료**, 이 로드맵에서 제외.
- 계획 목적: 안정성을 검증한 뒤 탐색 품질과 장기 처리를 확장하고, 이후 기존 PostgreSQL·웹에 통합.
- 주의: 후속 단계는 앞 단계의 진단과 테스트가 완료된 후 적용. 현재 Stage 1 패키지는 최적화 로직 자체를 수정하지 않음.

## 단계 1 — 동일 입력 반복 실행 및 원인 분리 (이번 ZIP)

**목적:** 동일한 원본 입력, 정책, 코드, 시점·5척 범위에서 결과를 20회 반복 실행하고 변화의 발생 지점을 구분한다.

- A: 검증된 원본 140항차·11선석·3탱크에서 실제 S5 첫 번째 창의 **초기 ETB 후보만** 20회 생성, 해시·후보 수·실패 원인 비교. CP-SAT 호출 안 함.
- B: 성공한 C 실행의 **첫 번째 창 최종 ETB 후보 도메인을 고정**한 뒤, 통합 CP-SAT 체선료 목적 및 Exact Inventory로 20회 독립 프로세스에서 재해결. 비용·ETB·선석·솔버 증명 상태 비교. B는 첫 창만의 실험이며 후속 Rolling 상태까지 포함하지 않음.
- C: 기존 `scripts/v5_full/run_stage.py`를 바꾸지 않고 S5 5척·72h/24h Rolling 2창을 **독립 프로세스로 20회** 실행. 각 완료 실행마다 `verify_resume.py`로 원본 기반 독립 재생을 확인.
- 보고: 시작/최종 후보 지문, 비용 분포(정수 센트), 선박별 ETB 최대/평균 편차(분), 선석 변경률, CP-SAT `OPTIMAL`/`FEASIBLE`/중단 이유, 버전·입력·정책 지문.
- 결론 구분: `초기 후보 불일치`, `적응형 후보 확장 차이`, `동일 후보에서 비용 차이`, `동일 비용에 ETB/선석 차이`, `시간 초과`, `재생 실패`.
- 불변 조건: 원본 데이터·계약 룰·재고·Dock 4-1/4-2·FIX ETB·Lock·CP-SAT 목적함수·DB·웹 수정 금지.
- 합격 증거: 20회 결과 JSON, 실행별 Checkpoint, 독립 재생 PASS, A/B/C 비교 JSON+CSV+Markdown. 문제 발생 시 원인별 증거 제출; 결과가 다르다고 임의로 최적화를 수정하지 않음.

## 단계 2 — 조건부 스케줄 안정화 + 탐색 품질·전체 범위 검증

**목적:** 단계 1에서 확인된 *원인만* 최소 변경으로 해결한다. 항상 체선료 최소화가 우선이다.

1. 초기 후보가 변하면 후보 생성 예산·절차·캐시/키·정렬을 재검토해 고정 도메인의 재현성을 우선 회복.
2. 후보는 같으나 시간제한으로 결과가 달라지면 결정적 탐색 예산 또는 검증된 후보 도메인 스냅샷 재사용 검토. 실행시간 상한 및 품질을 비교하고 검증 전용/운영 모드를 분리.
3. 동일한 최소 체선료의 일정이 복수이면 **사전식 2단계 최적화**: (1) 정수 센트 체선료 최소, (2) **동일 비용 경계**에서 승인된 기준 일정 대비 ETB 편차·선석 변경 최소. 최초 실행에는 안정된 동률 해소 키 사용. 1차 최적성 미증명 시 전역 동등 최적해라고 표기하지 않음.
4. 변경 전후 비용/ETB/선석/실행시간 비교 및 독립 물리·재고·정산 Replay. 원본 4-1·4-2 / GRT / 야간 도선 fail-closed 동작 유지.
5. 안정성·정확성을 확인하며 S5 전체 **5척 작업완료 및 누적 정산 확인** → S10 → S20 → R7 → R14 → FULL140으로 확대. 이 단계에서 원본 정책 미확정이나 창 수 부족으로 실패하면 `UNRESOLVED`로 분류하고 전역 불능으로 오판 금지.

**통과 기준:** 동일 조건 재실행에서 일정을 설명 가능한 방식으로 선택; 상위 목적의 비용 악화 없음; 독립 검증 PASS; Rolling 승인/Freeze 및 계약 회계 일치; 확장 게이트별 최종 완료 수와 상태 투명하게 보고.

## 단계 3 — PostgreSQL 전환 + 웹/리스크 의사결정 통합

**목적:** 안정화된 V5 엔진을 실제 데이터 운영 흐름에 연결한다.

1. 기존 PostgreSQL 단일 DB와 `public` 스키마를 V5 중심으로 재설계하고 원본 적재/무결성 검증. 구형 테이블 보존 의무는 없지만 **대상 DB 확인, 백업, 단계적 마이그레이션, 회귀** 없이 삭제 금지. 기존 DB Stage 1 ZIP이 있다면 최신 main과 다시 충돌 검사하여 재사용.
2. DB에 원본 해시·정책 버전·후보 도메인 해시·최적화 실행ID·체선료(정수 센트)·실행 메타데이터·검증/잠금/상태승계 결과 저장. 입력 DB roundtrip 결과와 파일 기반 결과 동등성 확인.
3. 웹에서 실행 데이터셋/시나리오 선택, 선석 간트차트(ETU 시점, 조건부 Switching), 세 탱크 재고 및 계약 비용, 동일 입력 재실행 안정성 지표와 변경 사유 표시.
4. 후보 A(체선료 최소), B(대기시간 최소), C(일정 안정성/리스크)와 ETA 지연·작업 지연·기상 충격 평가는 **엔진·데이터 및 보존된 상태가 검증된 다음** 붙인다. 결과의 비용/안정성/강건성 출처를 분리하고 LLM은 검증된 구조화 출력만 설명.

**통과 기준:** 실제 DB 재조회→엔진→Checkpoint→웹 전 과정 무결성; 파일 기반 결과 동등성; 사용자에게 승인·미검증·미결 상태를 구별해 표시; 보안·복구 경로 테스트.

## 우선순위 및 비범위

- 이번 **단계 1**은 기존 PR #69·#70 작업을 다시 하지 않는다.
- S5 2창 완료는 전체 5척 처리완료와 다르며, 72h 겹치는 창별 비용은 합산 누적 체선료가 아니다.
- `OPTIMAL`은 현재 창에서 **생성된 유한 ETB 후보 집합**에 대해서만 주장 가능하며 140항차/58일 전역 최적성이 아니다.
- 시험용 합성 정책의 통과는 현장 운영 승인이나 실제 계약 정산 증명이 아니다.
