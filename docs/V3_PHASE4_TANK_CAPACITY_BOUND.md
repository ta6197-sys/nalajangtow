# V3 single-tank capacity bound experiment

`V3_SINGLE_TANK_CAPACITY_BOUND_V1` is an optional candidate filter for the tank-allocation subproblem; the default is `DISABLED`. It never changes the externally supplied flow, vessel quantity, time, berth, FIX or Freeze constraints. Independent exact inventory replay remains mandatory. It is a necessary condition, not a complete feasibility test.

For a discharge using a single tank with no same-cargo vessel load in the modeled movements, the transfer can fit only if `cargo <= tank maximum - tank minimum + fixed external withdrawals during the transfer`. Positive external flow and all other discharges are ignored when computing this upper bound, making it conservative. Arithmetic uses `Fraction`, integer-second events, and actual signed six-hour inputs. Any unknown movement, carried transfer of the call, unreconciled cargo, missing or overlapping flow, malformed data, or same-group load disables the affected filter. If all tanks for a vessel would be filtered, the solver retains the original options so existing input validation and status handling remain authoritative. No tank-to-tank transfers are assumed.

Enable for an isolated day with `python -m benchmarks.v3_phase4_resume SNAPSHOT ROLLING --output OUTPUT --time-limit 120 --phase-release-policy LOCKED_ONLY_V1 --inventory-relaxation --reuse-physical-model --berth-search-heuristic CRUDE_INBOUND_FIRST_V1 --same-tank-policy ALLOW --capacity-bound`. Enable the separate 58-window experiment with `python -m benchmarks.v3_phase4_run_resumable SNAPSHOT --output-dir NEW_DIRECTORY --days 58 --seconds-per-strategy 60 --same-tank-policy ALLOW --phase-release-policy LOCKED_ONLY_V1 --capacity-bound`. The policy identifier is included in the run fingerprint; a different policy cannot silently resume an existing run.

Measured against the saved day-four 2026-11-06 state, using the same 120-second budget, main evaluated 43 berth candidates without an independently validated incumbent; the optional implementation evaluated 65 and also found no incumbent. These are one sequential observation each, not a speedup guarantee. An earlier temporary prototype evaluated 87, but did not include all production guardrails; do not treat it as the validated implementation's result. Both runs used ALLOW, locked-only release, inventory relaxation and identical snapshot and prior state. This does not prove the day infeasible, determine global optimality, or establish an executable full-period schedule.

Regression: full unittest discovery ran 407 tests with 405 passing and 2 skipped. The skipped tests require explicit isolated source PostgreSQL and the older named workbook fixture. New tests cover exact capacity and process-withdrawal boundaries, concurrent loading, carried transfers, incomplete/overlapping flows, subsecond input, immutable source objects and a solver allocation independently checked by the existing validator. Results under `results/v3_phase4/` are generated artifacts and are gitignored.

The new 58-window run `rolling_capacity_bound_v1` independently validated days 1–3, covering 14 distinct calls, and stopped at day 4 after its three 60-second strategies evaluated 71, 56 and 35 candidates without a validated incumbent. The new run uses its own carried state, so these counts are not a controlled comparison with the earlier rolling run. No later day was executed and no full-period cost has been established.
