# Phase 4B — standalone tank LP/MILP

Base `33437559909a1a531f37e92023182d943cab3812`; branch `feat/v2-phase4b-tank-milp`. This is an isolated, opt-in subproblem. It neither connects to the CP-SAT planner nor writes PostgreSQL or workbooks. It does not approve a schedule.

## Interface and policy

`solve_tank_allocation(network, vessel_requirements, transfer_windows, *, horizon_start_at, horizon_end_at, mode='AUTO', time_limit_seconds=30)` lives in `src.daily_planning.tank.optimization_service`. Inputs use the existing `TANK_NETWORK_V1` fields; each requirement uses the V1 call fields, with an optional `carried_volume_bbl`, and each transfer window has `call_id`, integer-second timezone-aware `start_at` / `end_at`, and optional `fixed_rate_bbl_per_hour`. The horizon and every window must be explicit. Unknown network/tank/connection operational fields are rejected rather than silently ignored. A carried volume requires the original tank ID. The original cargo equals carried plus remaining; only remaining quantity is scheduled, with an exact kg value derived from the supplied, checked density if mass is supplied. No density is invented.

All rates/windows/tank assignments fixed: run the existing deterministic validator, not an LP. Otherwise a fixed unique tank per vessel uses an LP. Alternative connected, same-cargo tanks use a MILP with one binary tank choice per vessel and binary activation per tank/time interval. `mode='MILP'` can also handle resource sequencing when fixed assignments have overlapping windows; the continuous LP rejects such cases with `UNSUPPORTED_SHARED_RESOURCE_SEQUENCE` rather than silently allowing simultaneous use. Fixed and variable windows may coexist; fixed rates are kept exactly. Each tank and berth serves at most one transfer per interval, matching the conservative V1 validator. Additional pump and pipeline interactions remain unknown and cannot be inferred.

The constant objective is 0: the model tests feasibility, not a cost, throughput or global scheduling optimum. State variables are in 1,000 bbl; q is transferred volume in 1,000 bbl, and rate capacity uses the exact duration expressed in hours. Inventory balance adds discharge, subtracts loading, and adds the externally supplied fixed tank net process flow. All tank bounds apply at each 30-minute reporting point and at each supplied window boundary, including second-level boundaries. Rates/activations are constant on these elementary intervals. Optimizer-created starts/stops inside an elementary interval are not represented; the domain is therefore conservative. Availability endpoints are preserved and physical events are not forced onto the reporting grid. No inter-tank transfers or vessel reassignment are modeled.

## Numerical and status policy

HiGHS primal, dual and MIP tolerances are 1e-7; because the volume scale is 1,000 bbl, a primal tolerance unit corresponds to 0.0001 bbl for a directly scaled volume row. Solver results are reconstructed as finite decimal rates, with 1e-9 bbl/h rate quantization and a bounded, reported exact residual correction on a variable-rate segment. Fixed-rate segments are never adjusted. Every candidate then passes the existing `validate_schedule()` and `project_inventory()` exact-Fraction checks. If reconciliation cannot be represented, exceeds the declared tolerance, or exact validation fails, the schedule is rejected as `NUMERICAL_VALIDATION_FAILED` and is not returned. Cargo reconciliation reports original, carried, remaining and exactly scheduled volumes. No mass, volume, or process outflow is silently changed.

The service returns model version, input fingerprint, chosen tanks, schedule, inventory, timing/counts, solver status, objective/bound when applicable, tolerances, exact validation status and `operational_approval: false`. Statuses include `OPTIMAL`, `FEASIBLE`, `INFEASIBLE`, `TIME_LIMIT_NO_INCUMBENT`, `INVALID_INPUT`, `NUMERICAL_VALIDATION_FAILED`, `MISSING_PHYSICAL_DATA`, `SOLVER_UNAVAILABLE`, and `SOLVER_ERROR`. `OPTIMAL` is only HiGHS' result for this zero-objective finite formulation. A proven general MILP infeasibility is reported as `TANK_ALLOCATION_INFEASIBLE`; it is not guessed to be caused by one specific tank or pump. No-incumbent timeout is not called infeasibility. `time_limit_seconds` limits the solver call, not input preparation or exact validation.

## Reproduction and synthetic benchmark

Optional dependencies: `pip install -r requirements-tank.txt`. They are not required by the legacy runtime. Run `python -m unittest tests.test_v2_tank_milp` and `python benchmarks/v2_tank_milp.py`. Measured using Python 3.11, Pyomo 6.10.1 and HiGHS 1.15.1; three repeats on the existing explicitly synthetic 30-tank network and two vessel fixture. Results and exact input fingerprints are in `benchmarks/v2_tank_milp_results.json`. Deterministic transfer rates are fixed; LP/MILP allow variable rates. The MILP comparison forces one eligible tank per vessel to retain the same topology; the separate MILP selection case includes another compatible synthetic tank and a full first tank. These are not identical feasible domains and are not production timings. Times below are medians in seconds; cold LP first-run total was 0.13098 s because imports/solver startup are included in total.

Numerical reconciliation: in the first three variants, TANK-01 ends at exactly 526,000 bbl = 500,000 + 30,000 discharge − 4 hours × 1,000 outflow, and TANK-04 at exactly 190,000 bbl = 200,000 − 8,000 load − 4 hours × 500 outflow. In the separate full-tank selection case the model chooses TANK-02 and ends it at exactly 530,000 bbl; TANK-01 stays at 1,000,000. Objective/bound zero proves only feasibility of the modeled intervals. The measurements show deterministic simulation was quicker in these small fixtures; they do not establish LP versus MILP performance generally.

## Validation and outstanding integration

23 new synthetic unit tests cover fixed LP, alternative tank selection, full tanks, missing connections, incompatible cargo, connection rate, fixed outflow, sub-grid events and overflow, no splitting, shared resources, beyond-72h completion, density, carried work, exact validator rejection, time limit, stable fingerprints and input immutability. Existing 14 V1 tank tests pass. Full suite with optional dependencies: 233 tests, 232 passed, one existing PostgreSQL initial-state integration test skipped. In the legacy environment without optional packages, 233 tests ran with 209 passed and 24 skipped (23 optimizer tests plus the existing fresh-state PostgreSQL test). An explicit optimization request reports `SOLVER_UNAVAILABLE`; ordinary scheduler use does not import those packages.

Real tank-specific capacities, cargo groups, initial stocks, source density, berth connectivity, transfer rates, fixed process plans and shared pipeline/pump constraints remain required. Phase 3 pilotage, switching, tug, FIX and cross-berth operating policies remain incomplete. For Phase 5, pass immutable network and vessel/window snapshots to this service, independently revalidate returned time/occupancy impacts, and feed back only proven exclusions. The present model is not a live operations decision or production default; no Phase 5 integration was performed.
