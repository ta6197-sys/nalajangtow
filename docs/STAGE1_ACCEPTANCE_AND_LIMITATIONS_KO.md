# Docktimize V5 — 남은 1단계 통합 실행/검증 설계

## 기준
- 최신 확인 `main`: `86a1e989f17e2de8293101277a0db8d11a6ab116` (PR #75 병합).
- 기존 CP-SAT/정확한 재고/계약 정산/동적 Lock/ETU와 Stage 2A~2C 감사 도구를 모두 재사용.
- 실제 V5 합성 데이터 140항차, 선석 11, 탱크 3, FIX 15 및 6시간 공정유량 696개가 있어야 시작 가능.
- 운영 승인 `false`. 기존 소스·정책·체선료 수식·Docker·DB·웹 수정 금지.

## 실행 순서
1. 원본 및 계약·도선·일광·고정 외부유량의 적법한 입력 확인. `--mode preflight`에서 게이트별 필요 미래 72시간 범위 확인.
2. Stage 2B: 60초 20회 + 120초 20회 원자료 존재 시 새 폴더로 재분석, 없으면 원래 실험 실행. 모든 실행 Replay, 후보·물리 일정 지문, 원 단위 아닌 정수 센트 비용 비교. 변동이 있으면 자동 진행 중단.
3. S5 완료: 3창에서 5척 ETU 및 전량 이송·정산 확인. 아직 완료되지 않고 나머지가 정상이라면 4~8창의 **새 실행**을 차례로 검증. 입력 커버리지 부족 시 중단.
4. S10·S20: 각각 기존 3창을 독립 실행, 72h/24h 물리·재고·계약·승계·독립 Replay 확인. 10/20척 **전체 완료와 단순 창 통과는 구분**.
5. R7·R14: 동일한 S20 20척으로 7·14창 Rolling 검증. 미완료 항차·정산 지연·재고 경계 별도 기록.
6. FULL140: 140척 60창. **140척 전부 ETU 완료 + 계약별 정수 센트 확정 + 독립 Replay PASS**만 통과.

## 중요 사전 차단
- 60창은 24시간씩 59회 전진하고 마지막 창에서 72시간 미래를 참조하므로 최초 `as_of_at`부터 **62일**의 미래 범위가 필요.
- 현재 알려진 696개 × 6시간 공정유량 × 3개 탱크 기준 각 탱크 232개 기록, 약 **58일**. 전체 60창에 필요한 끝 시각까지 실제 기록이 없다면 `FIXED_FLOW_HORIZON_SHORT` 차단.
- 또한 기존 `V5_USER_ETU_SWITCHING_20261112_V1` 운영정책에 선석별 명시된 작업/도선 허용 창이 그보다 짧을 수 있음. 출처 없는 연장·복제는 절대 금지.
- 예산 증가에 따른 후보영역 변화는 유한 후보 최적성과 전역 최적성의 차이를 보장하지 않음.
- 기존 `MAX_GROUPS=12`를 임의로 140으로 키우지 말 것. 큰 계획창의 정규 동률 선택 미증명·생략을 그대로 기록.

## 주요 결과
- `stage1_summary.json` / `.md`: 전체 요약 및 처음 차단된 게이트.
- `stage2b_gate.json`: 40회 실험의 맥락·불완전성·변동성 평가.
- `stage2b_reanalysis/stage2b_report.json`: PR #75 기준 새 분석, 기존 파일 보존.
- S5 원래 `stage2c_completion_audit.json`: 모든 선박의 작업 및 정산 완료 감정.
- S10/S20/R7/R14/FULL140 각 `step_record.json`: 지정 창 검증·독립 Replay·완료 개수·정산 및 각 창의 비용·후보·증명 상태.
- 각 실행의 원본 체크포인트와 전체 stdout/stderr를 절대 덮어쓰지 않음.

## 절대 혼동 금지
1. **창 검증 완료**와 **모든 항차 작업 완료**는 다름.
2. 동일 입력 **재현성**과 후보영역 **OPTIMAL 증명**, 승인 일정 **안정성**, 충격 **강건성**은 서로 다름.
3. 중첩되는 72h 예상 체선료를 합산하면 중복 계산임.
4. 전체 140항차 및 DB·웹 E2E 성공은 실제 실행 증거 없이는 주장할 수 없음.
5. Stage 2 PostgreSQL·API·웹 코드는 이번 ZIP에 없음. 1단계 합격 후 설계·통합 진행.

## 한계 및 위험
이 패키지는 사용자의 원본 데이터를 갖고 있지 않아 실제 S5~FULL140을 실행하지 않았다. 내부 테스트는 예시 입력으로 만든 **순수 감사·오케스트레이션 단위 테스트**다. Codex는 최신 원격 `main`과 실데이터 실행에 대한 별도 통합 테스트를 수행해야 한다. 명시된 정책·공정유량 부족은 알고리즘 수정을 허용하지 않는다.
